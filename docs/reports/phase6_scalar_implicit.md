## 1. The port

`core/include/cfdcore/scalar.hpp` and `core/src/scalar.cpp`, namespace `cfdcore::scalar`, after
part a's flux. Every value the reference keeps is formed by the reference's operations in the
reference's order, one rounding each (`-ffp-contract=off`), over every cell, SOLID and held cells
included, as the reference's whole-array expressions form them. A value the reference forms and
then overwrites with a constant (a SOLID cell's Jacobi update, set to zero) the core need not
form, and does not. The templates take the direction count `D`, instantiated at 1 and 2, and
walk the cell field by rows (lines along direction 0), forming each row's stencil once
(`row_stencil`: the row's faces and whether it has a row below and above), so the per-cell loop
does no division.

- **The set-up, `implicit_system`** (`implicit_step` before the solve). The diagonal's extra terms
  per cell in the reference's order, west, east (direction 0's low then high face), south, north,
  then the sink; whether any is non-zero (`.any()`: a NaN counts, a -0.0 does not); then
  `V / dt`, `a_P = V / dt + extra`, `b = (V / dt) C*` and the stop, `tol` times the largest
  `|b|` over every cell, NaN when a `|b|` is NaN as `np.abs(b).max()` gives it. The refusal of a
  negative or NaN bound is `check_leftover_bound`, a status the binding turns into the
  reference's `ValueError`; the method's name and a bool bound (Python's or NumPy's) are the
  binding's to refuse, before the bound's value, in the reference's order. When nothing diffuses
  or sinks, `implicit_step` returns `C*` with no solve, as the reference does.
- **The acceptance, `acceptance`** (`_Acceptance`). `test` is called with the residual of an
  iterate that met the max-norm stop; with a bound it forms the leftover and accepts when
  `|leftover| <= bound`, without one it forms nothing. `final` forms the returned field's
  leftover unless the last formation was from that same residual. The reference tells residuals
  apart by array identity; the core's residual is one scratch array, so each solver numbers the
  residuals it forms and the acceptance compares numbers. A residual updated in place (CG's
  recursion) keeps its number, as the reference's array keeps its identity. The leftover is
  `dt * pairwise_sum(r)` with a scalar step, and `pairwise_sum(dt_masked * r)` with a per-cell
  step, `dt_masked` zero in SOLID cells (where a per-cell step need not be finite). Both sums are
  `reduce::pairwise_sum`, NumPy's order, on a contiguous array of the cell field's length.
- **`jacobi`** (`_jacobi`). From `C*` as given (its SOLID values included: the reference's first
  residual reads them). Each sweep forms `r = (b + sum_f G_f C_N) - a_P C` with the neighbour sum
  east, west, north, south and a missing neighbour read as zero (the reference's zero padding),
  zeroes `r` in SOLID and held cells, takes the largest `|r|` (NaN-propagating), and forms the
  next iterate `C + r / a_P` with SOLID cells zero in the same pass. The stop is the max-norm test
  and then `accept.test`; at the cap it ends; else the next iterate becomes the iterate. The
  returned field is the iterate whose residual was last formed, as the reference returns it.
- **`conjugate_gradient`** (`_conjugate_gradient`). From `C*` with SOLID cells zero; SOLID and
  held cells fixed (residual and product zero there); the inverse diagonal zero at fixed cells;
  the true residual; the stop and acceptance on it at the start; then Hestenes and Stiefel with
  the residual recursion `r <- r - alpha q`, the true residual formed when the recursion meets
  the stop or at the cap, the solve ending converged only if that meets the stop and the
  acceptance takes it, else restarting from it (`z = inverse r`, `p = z`). The direction is
  updated `p <- p * beta`, then `p <- p + z`, in that order.
- **The fallback** (in `implicit_step`). A CG solve that did not converge, or left a value at or
  below zero (or NaN) in a cell it solves for, is discarded; a fresh acceptance and a Jacobi
  solve from `C*`, not from the CG iterate. The result's iterations are the CG's, its converged
  flag, sweeps and leftover the fallback's.
- **The result, `implicit_result`** (`ImplicitResult`): the method, iterations, converged,
  fallbacks, fallback sweeps and leftover, and two counts the reference does not return:
  `leftover_sums`, how many times a leftover was summed over the cells (ADR-016's cost, "formed
  only after the max-norm test holds"), and `restarts`. The field goes to the caller's `out`.
- **The scratch, `implicit_scratch`**: every array a solve needs (a_P, b, the iterate and the
  next, the residual, the CG's inverse diagonal, z, p and q, the masked step and the leftover's
  terms), allocated once on a layout, so a solve allocates nothing.

**The dot product's partition.** The CG's two dot products per iteration go through
`reduce::blocked_dot` (ADR-017 G, the second kind), with a block per row of the cell field: the
products `a_i b_i` of each row, one rounding each, summed in `pairwise_sum`'s order (NumPy's
pairwise sum, without its leading 0.0), and the row sums added to 0.0 in row order. The reasons:

- the partition is fixed by the grid, never by a thread count, so a threaded or device build that
  computes the rows apart and adds them in order gives the same bits (ADR-017 G);
- a row is a line of the layout (`layout::lines(0)`), contiguous in memory, which is the unit a
  CPU thread or a CUDA block takes in steps 3 to 7, and it exists in any `D`;
- 30 to 120 rows on the product grids are enough blocks for the CPU's threads;
- a pairwise sum inside the row keeps the rounding's growth in the row's length logarithmic, as
  NumPy's sums are, rather than linear as a left-to-right sum's is.

One pairwise sum over the whole field is fixed too, but its splits fall where `n / 2` rounded
down to eight lands, not at rows, so a parallel version would cut rows between workers. The
partition shows in the tests: the plant `one_block` (T5) sums the core's dot products as one
block and fails the comparison with the core's dot products. `_cfdcore.row_dot(a, b)` exposes
the same product for two [ny, nx] arrays.

**The binding** (`core/python/bindings.cpp`): `ImplicitScratch2(grid)` (keeps its grid alive;
`diagonal()` and `rhs()` return copies of a_P and b), `implicit_system(scratch, c_star, volume,
dt, g_u, g_v, diagonal, tol)` returning `(diffuses, stop)`, `implicit_step(scratch, c_star,
volume, dt, g_u, g_v, diagonal, solid, tol, max_iter, out, held=None, method="jacobi",
leftover_bound=None)` returning an `ImplicitResult2`, and `row_dot(a, b)`. `dt` is a number (a
Python float, a NumPy scalar or a 0-d array, as `np.ndim(dt) == 0` reads it) or a C-contiguous
float64 [ny, nx] array. The arrays cross in their own layout, read-only, C-contiguous and
aligned; a wrong dtype, dimension, layout or shape, an unaligned array, an `out` sharing memory
with an input or a bool bound is a `TypeError`; an unknown method or a negative or NaN bound a
`ValueError` with the reference's message.

## Findings

- **F1, prediction (c) fails: the core's Jacobi solve is not ten times the reference's.** (c) is
  scored on T6, run 1, by the rule committed with it, and fails in every class; runs 2 and 3 agree.
  T6b puts the cost in the sweep loop, which the compiler does not vectorise (section 6). Part a's
  flux gained more (prompt 87, T6b there); the reference's flux is a longer chain of array
  operations per face (`advective_flux`) than its sweep is per cell (`_jacobi`). For the march (step 3) and the end-to-end
  timing (step 6) this means the implicit solve as built is not a tenfold speed-up of the
  reference's. The change to try, if a later step needs the speed, is a sweep loop the compiler
  can vectorise: the row's first and last cells taken apart from its interior, and the SOLID and
  held masks applied as selects. Every operation would stay elementwise in the same order, and
  the parity tests here would show whether a bit moved; T6 and T6b are the timing to set it
  against.
- **F2, at a tolerance near rounding the CG's count can differ from the reference's.** At the
  configuration's tolerance, 1e-10, every planted CG solve and every captured one stops at the
  reference's count (T3, T4b). At 1e-15 some of the tight cases do not, and each of them
  restarts (T3): the recursion meets the stop and the true residual does not, so whether a
  confirmation passes depends on the dot products' last bits, which are OpenBLAS's in one solve and
  the core's row sums in the other. In two of them one solve reached its cap and fell back to
  Jacobi while the other converged, so their fields differ by the gap between a converged CG field
  and an unconverged Jacobi one. Where the counts agree the fields are well within the rule (T3).
  This is the case ADR-017 G's rule provides for (the differing counts reported apart), and no
  captured solve is near it. Step 5 (the outer iteration, `turbulence`) should expect it if a k or
  eps system is solved near its rounding floor.
- **F3, one plant is equivalent: `p` updated as `z + beta p`.** IEEE 754 addition and multiplication
  are commutative, so `z + beta * p` and `p * beta + z` are the same two roundings of the same
  operands, and no test can tell them apart (T5). The order that can matter is a fused
  multiply-add, which `-ffp-contract=off` forbids; that plant (`p_fused`) fails the comparison with
  the core's dot products.

## Deviations and limits

- The binding takes the output field (`out`) and the scratch instead of returning a new array, so
  a solve allocates nothing; the reference returns a new array, and `C*` itself on the early
  return, where the core writes a copy of `C*`.
- `ImplicitResult2` carries two counts the reference does not return, `leftover_sums` and
  `restarts`; `implicit_system`, `ImplicitScratch2.diagonal()` and `rhs()` and `row_dot` exist for
  the tests.
- The acceptance tells residuals apart by a number each solver gives them, where the reference
  uses array identity (section 1). The two agree on every path of both solvers: the only residual
  the reference updates in place (CG's recursion) is replaced by a true residual before any
  `final` reads it.
- **Bit for bit is a claim about finite inputs**, as in part a: no planted or captured input holds
  a NaN, and the solvers refuse a non-finite field before the solve.
- With a per-cell step that is infinite in a SOLID cell, the reference divides 0 by 0 there
  (`c + residual / a_p` before `c[solid] = 0.0`) and NumPy warns; the value is discarded. The
  core writes zero to a SOLID cell's update without forming the quotient. The parity tests that plant such a step
  silence that one warning (`REFERENCE_DIVIDES_BY_ZERO`). No caller hands in such a step: the
  transport step is one number and k-epsilon's pseudo-time step is finite in SOLID cells.
- An unaligned bool array cannot exist (a bool is one byte), so the refusal tests have no such
  case for `solid` and `held`.
- The captures are not committed (`results/builder88/captures/`, 140 calls, about 105 MB).
