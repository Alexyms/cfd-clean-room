## Decisions already taken (Alex, 2026-11-15), recorded as given

1. **Linux is the primary target.** The core is built and run under WSL2 from this one Windows
   checkout. The code stays portable: standard C++, CMake, nothing Windows-specific. Revisit only
   if the shared checkout becomes a real hindrance.
2. **The whole step moves to C++.** The flow solve's outer iteration and the march's step, every
   stage the profile timed, with the fields resident in the core for a run. Python sets up a run
   and reads its results. Not the plan's two kernels.
   *Evidence.* The plan's two kernels, the pressure CG loop with its V-cycles and the transport's
   advection-diffusion stencil, hold 56.4%, 58.3% and 63.8% of the 80x30, 160x60 and 320x120
   runs; if they took no time the runs would be 2.29, 2.40 and 2.76 times faster (T12). Most of
   the flow solve is outside the CG loop: the pressure correction is about two fifths of an
   outer iteration on every grid (38.7%, 35.7% and 41.1% by the solver's own clock; T3, and
   the profile's stop-condition section), the momentum predictor and the turbulence update a
   quarter each. A loop port also hands scalars back to Python every iteration: three per CG
   iteration, one per Jacobi pass, about twenty-two per class step for the booking (T7).
3. **The order.** The C++ core on the CPU; then CUDA on the same 2D problem, a low-stakes first
   GPU venture; then the true 3D model through a Phase 6 ECR. *Amended by Alex, 2026-11-16:* the
   3D model is its own phase, Phase 8, after Phase 7 (section J).
   *Evidence.* A 320x120 field is 0.29 MiB and the largest kernel moves 8.4 MiB per execution,
   inside the GPU's 32 MiB L2 (T9): on the 2D grids the GPU's DRAM bandwidth is not the limit,
   and whether FP64 pays turns on an L2 bandwidth the profile could not measure (T9b). The 2D
   problem is where that can be measured against a CPU core that already matches the reference.
   VAL-021 was closed as a documented gap because no published measurement fits a 2D slice, so
   the transport's turbulent spreading stays unvalidated against measurement until a 3D model
   can be compared with one (`docs/PROJECT_PLAN.md`, the Phase 3 amendment of 2026-10-15).
4. **Written per direction.** The core's grid, fields and stencils take the number of directions
   as a parameter, so the true 3D model reuses the arithmetic; only 2D is implemented and tested
   now. No 3D feature is built early.
   *Alex, 2026-11-23 (prompt 92b):* the momentum module, which step 4a built for two directions
   only because its stencil has one transverse direction, takes the number of directions as a
   parameter too, so that it is ready to generalise to the true 3D model, where each component has
   two. What needs a pair of directions is written per ordered pair of a component and a transverse
   direction (`docs/reports/phase6_momentum.md`, section 7, with what the 3D model would add and
   where).
5. **Precision.** The CPU core is double precision throughout. In the CUDA step single precision
   may be used stage by stage where a measurement shows it pays, the advective flux and its
   limiter first, with running totals, residuals, stopping tests and the particle budget kept in
   double.
   *Evidence.* The advective fluxes and limiter are the march's largest stage on every grid
   (40.6% of the 320x120 march, T6) and the only stage above the GPU's FP64 balance against
   DRAM, at 1.23 operations per byte against 0.69 to 1.22 (T7, T8); the FP32 balance is 44 to 78.
   ADR-016's stop reads the sign and size of a sum, and ADR-013's a residual norm against a
   floor of 1e-13 of the flux scale, so those stay in double.
6. **Parity at two levels.** Each building block, given identical inputs, matches the Python
   reference to about 1e-12 relative, or bit for bit where the Python's order of operations is
   copied. A whole run is benchmarked on its results: the decisions (detection latencies, clear
   times, the layouts' ranking, the budget against REQ-T05) and the fields agree within the
   system's own error noise, defined by measurement (this pass's probe). Where single precision
   is used, the same benchmark applies.

(4) Windows Python driving a WSL2 process through `wsl.exe` and files or a socket. It keeps one

tested block by block from the Windows suite.
*Recommendation.* (1). A Windows build is available on this machine and is still not
recommended, for option (3)'s remaining reasons. The C++ standard is C++20: `std::span` for the arrays the binding hands
in, concepts for the direction count, designated initialisers for the setup structs; CUDA 12
added the C++20 dialect to nvcc, which the CUDA step confirms on its release. C++17 would serve, at the cost of hand-written
spans; C++23's `std::mdspan` is not in GCC 13's library. The toolchain step's gate (section
J) includes the Python reference run under WSL2 against this machine's Windows records, since
glibc's `exp`, `log` and `pow` and the platform's OpenBLAS build may change the last bits.

**B. How Python calls the core (section B).**
*Picture.* With the fields resident, Python holds a handle to a run in the core and calls it a
few times per interval: a steady solve in chunks between steady checkpoints, a march in chunks
between output steps. At the profile's costs a march step on 80x30 is 11.65 ms in Python (T4);
even at a hundred times faster, a call per step is about 117 microseconds of work against about a
microsecond of call overhead. The parity tests call the blocks one by one on the reference's
arrays.
*Options, ranked.*
(1) nanobind: a C++17 binding library (by pybind11's author) with an `ndarray` type that takes
NumPy arrays without copying and states their dtype, shape and C order in the signature, and
that speaks DLPack, so at the CUDA step a device array can be handed to CuPy or PyTorch for
inspection without a copy. Smaller and faster to build than pybind11.
(2) pybind11: what REQ-S06 and ADR-005 name, the most widely known; NumPy arrays through
`py::array_t`, no DLPack without hand-written code.
(3) A C interface through ctypes: CLAUDE.md's current rule, no build dependency on Python, but
a run's lifetime, its errors and every array's shape and dtype handled by hand on both sides,
and no exceptions across the boundary.
(4) A separate executable reading the configuration and writing run files: the cleanest
isolation, but the monitor and the parity tests could not reach the step, and the core would
have to parse YAML and write HDF5, which CLAUDE.md keeps in Python.
*Recommendation.* (1), with the core a C++ library that knows nothing of Python and the binding
one thin target beside it (`core/python/`), so that changing the binding later touches one
directory. REQ-S06's "via pybind11" is then amended (section I).

**C. The core's modules (section C).**
*Picture.* One module per stage as the profile named them, each owning its arithmetic and its
scratch arrays, handed typed arrays and scalars and returning typed results, with no module
reaching into another's state: the project's modular, isolated style (MOSA). The Python
modules that interpret the configuration (the boundary registry, the boundary layers, the
vents, the particles, the scenarios) stay in Python and hand the core arrays.
*Options, ranked.* (1) Section C's map: a stage per module, a run object that owns the resident
fields and calls the stages in the reference's order. (2) One module per Python module, a
direct transliteration: simpler to trace line by line, but `solver_transport.py` and
`turbulence.py` each hold several stages and the parity tests would test them only together.
(3) A kernel library with the step's loop in Python: decision 2 rules it out.
*Recommendation.* (1).

**D. Tests (section D).**
*Options, ranked.* (1) GoogleTest for the core's own tests, run by CTest, fetched at a pinned
release by CMake's `FetchContent`; the building-block parity tests in pytest beside the Python
suite (`tests/test_core_parity.py`), marked `parity` and skipped with a reason when the core

CTest. (3) Parity tests in C++ against arrays the reference saved to disk: no Python in the C++

*Recommendation.* (1). The C++ tests check what needs no reference (a stencil on a planted

**E. What stays in Python (section E).** Configuration and its validation, the mesh's

**G. Threads and determinism (section G).**

thread count, which the end-to-end benchmark would then have to absorb.
*Recommendation.* (1).

## Context

and the transport's stencil (`docs/PROJECT_PLAN.md`, Phase 6 as it stood before this record).
Prompt 84 measured where a scenario run's time goes. On 320x120 the march is about four fifths
of the run; within it the advective fluxes and limiter take 40.6%, the implicit solve 34.9%,

320x120 and a march step two and a half times (T5), so Python's fixed cost per call is visible

the march (T4, T6).

The project's present compiled-code rules (CLAUDE.md, "C Coding Standards") were written for
the two-kernel plan: C in `csolver/`, a Makefile, ctypes, raw pointers and dimensions, and no
boundary conditions in compiled code. `csolver/` does not exist yet; nothing has been built.

  processor without AVX2 cannot run the module. `-ffp-contract=off` stays, so the FMA the target

  target the limited QUICK flux is a block of `lanes.hpp`, where under the baseline x86-64 a loop

- `std::experimental::simd` is not adopted. The core keeps the block style of `lanes.hpp`, and
  revisits the choice when C++26's `std::simd` is in the toolchain's library. Every step's report
  keeps timing its kernels, so that a change that silently loses vectorisation (the report's F8)
  shows.

## B. The binding and the exchange

The binding module `_cfdcore` exposes three things: the setup types (plain structs of arrays and
scalars), a `Run` handle that owns the resident fields, and each module's building blocks as
free functions for the parity tests. Arrays cross as `nb::ndarray<const double, nb::c_contig>`
of a stated shape, so a wrong dtype, layout or shape is refused at the call with a `TypeError`,
which is what REQ-N03's rationale ("memory layout, dtype, or indexing errors") asked a test to
catch. Arrays leave as new NumPy arrays (copies) when Python asks: at a frame, a checkpoint and
the end. A core error (a non-finite value, a breach of ADR-016's limit, a solve at its cap)
returns a status, which the binding raises as an exception of the core's own, carrying its
numbers (`_cfdcore.ConservationBreach`; amended 2026-11-22, fix pass 90b); the Python side
maps it to the exception the reference raises (`ConservationBreachError`,
`FlowNotConvergedError`, `PositivityError`), in `tests/core_mapping.py` until step 6's
`src/core_backend.py`, so `scripts/run_scenario.py` exits as it does today. The binding
imports nothing from `src`.

**The per-call exchange, a run.**

| Call | Python hands in | The core returns |
|---|---|---|
| `Run(setup)` | the mesh's per-direction geometry and cell types, the constants, the solver keys | a handle |
| `flow_state(boundary, initial)` | one flow state's velocity boundary data (section E), the warm start | nothing; the state is resident |
| `solve_steady(max_outer)` | the chunk's outer count (the steady checkpoint's cadence) | the stop's state (stopped, reason, outer count), the rule's readings, the residual history of the chunk |
| `flow_fields()` | | u, v, p, k, eps, nu_t, for the run file |
| `interval(plan, conditions, sources)` | the interval's step and step count, each class's concentration face data, the source rates | nothing |
| `march(n)` | at most n steps (to the next output, checkpoint or interval end) | per step: the time, each class's budget, the sensor readings and channels; whether the hold or a breach stopped it |
| `class_fields()`, `arrival()`, `recovery()` | | the arrays, for the frame, the checkpoint and the end |
| `restore(...)` | a checkpoint's fields, budgets, arrival maps, recovery fields | nothing; the next step is the uninterrupted run's |

The monitor's alerts read the readings the march returns, step by step, as they read the fields'
sensor cells now; nothing they do feeds back into the march (REQ-A06), so a batch of steps is
the same as one at a time. The clean-out's hold does feed back, so the recovery tracker is in
the core and stops `march` at the hold step.

## F. What the core must carry exactly

These are the contracts whose order of operations decides a stop, a refusal or a recorded
number; a port that changes them changes results by more than rounding.

- **The budgeted implicit stop (ADR-016).** The max-norm test first; then the leftover formed
  from the residual that test read, `dt` times its sum (scalar `dt`), and accepted when within
  `leftover_share * conservation_limit * S_n * dt_n / t_end`, evaluated in that order, with
  `S_n` holding step n's inflow and source. The leftover booked as `MassBudget.leftover`, the
  residual defined with it, and the breach test after every step at `conservation_limit` times
  the supply. The probe's sequential variant changed this sum's order on every run (P7).
- **The cumulative channels (ADR-015 C, as amended 2026-11-14).** Channel k reads class k and
  every class at or above its diameter, summed from zero, largest first, as
  `monitor.channel_sums` sums them, so the reading at a sensor's cell equals the field sum read
  there bit for bit; the arrival maps per event, channel and cell, the first step time at or
  after the onset at or above class k's threshold; the recovery fields on the same channels.
- **The pressure correction (ADR-013, as amended 2026-10-14).** CG preconditioned by one
  symmetric V-cycle of additive-correction multigrid (2x2 aggregation, exact Galerkin coarse
  operators, weighted Jacobi smoothing at 2/3, the coarsest level's dense pseudo-inverse), from
  p' = 0, to `||r||_2 <= pressure_rtol ||b||_2` or the floor `1e-13 F`, confirmed on the true
  residual at exit, or to the cap, which is reported; on a closed domain b projected onto the
  range and p' pinned; the diagonal preconditioner beside it as the parity path.
- **The k-epsilon model and the wall functions (ADR-012).** The standard and RNG variants'
  constants; k and eps advected by upwind (the default) or UMIST in pseudo-time at the
  turbulence Courant number; explicit growth from the strain, implicit decay and diffusion by
  CG to `turbulence.tol` with the Jacobi fallback on the cap or a non-positive value; nu_t
  relaxed by `alpha_turbulence`; the positivity test after every step; the scalable wall
  functions' wall viscosity, wall conditions and inlet values.
- **The stopping rule (ADR-011 G, ADR-012).** `error_estimate`'s conditions (a) to (e), its
  window and its version, as `stopping.py` defines them.
- **The scenarios' boundary changes (ADR-014).** A flow state per distinct velocity boundary,
  warm-started from the one before; each interval divided into equal steps under the stable
  step, its last step landing on the interval's end exactly (`IntervalPlan.time`); the fields
  and budgets carried across a switch; each interval's concentration boundary and sources; the
  vents' recirculation (ADR-014 J). Python keeps the event model; the core receives each
  interval's data.
- **Restart.** The resident state the checkpoint needs (the class fields, the budgets, the
  arrival maps, the recovery fields, the flow state at a steady checkpoint) leaves and returns
  exactly, so a restart is the uninterrupted run bit for bit, as ADR-014 D requires of the
  reference.

## G. Threads and determinism

Every sum, dot product and maximum in the core goes through `reduce`, which partitions the cells
into fixed blocks (a block a row, say) and combines the blocks' results in block order. The
result then does not depend on how many threads compute the blocks, so the CPU core can be
single-threaded first and parallel later with no change in any bit, and two runs of one build
on one machine are identical.

**Which sums copy NumPy's order (review 85 S1).** A sum that a stop, a refusal or a budget
reads is formed in the reference's order and compared bit for bit at level 1:

- the implicit solve's leftover, `dt` times the sum of the residual, which ADR-016's stop reads;
- the stopping rule's signed sums over the cells (`error_estimate`'s conditions (c) and (d));
- the budget's terms, the content and every boundary and deposition sum, which the breach test
  and REQ-T05 read;
- the cumulative channels, whose order ADR-015 C already fixes (section F).

NumPy sums a contiguous array pairwise: blocks of up to 128 elements, each summed with eight
accumulators, combined by recursive halving above that. This is as the builder knows it, not
read again for this pass; step 2's first test confirms it against NumPy on the reference's own
arrays, strided slices included, and a sum whose order cannot be copied is moved to the second
kind with the reason recorded. The pairwise order is a fixed tree, so its subtrees can later go
to threads and be combined in the same order without changing a bit: the copied sums keep this
section's determinism. Every other reduction (the CG's dot products, which NumPy hands to
OpenBLAS, and the residual norms) goes through the fixed blocks above and is compared at 1e-12;
a maximum is exact in any order. The CG's stop reads a norm of this second kind, so a CG is
compared at level 1 for the reference's iteration count, with its differing stop tests counted
(section I).

**What 1e-12 is relative to, for a sum.** A sum's rounding is proportional to the sum of its
terms' magnitudes, not to its result. P7's order change moved the leftover by up to 2.1e-11 of
itself because the leftover is a cancelling sum, small beside its terms. Level 1 therefore
compares a sum relative to the sum of its terms' magnitudes (section I), and every other output
relative to its largest magnitude. A missing or doubled term moves a sum by that term, decades
above 1e-12 of the magnitudes, so the comparison stays sharp.

**A pseudo-inverse, and a chain of blocks (Alex, 2026-11-25, after prompt 93b).** Inverting a
matrix of condition kappa turns rounding at eps into errors of about kappa eps for any correct
method, LAPACK's included, so a fixed 1e-12 asks an ill-conditioned coarsest system for digits
neither answer has. Level 1 judges a pseudo-inverse against its condition on the operator's
range: the core's and NumPy's matrices each within `4 n kappa eps max|X|` of an
extended-precision referee X, and within twice that of each other (prompt 93b, set before its
runs). And a chain of blocks, a whole pressure correction say, is judged block by block, each
given the same inputs: the corrected velocity given p' is a block of the first kind, bit for
bit, and p' is judged by the CG rule; the chain's own differences, which a block downstream can
amplify (a velocity formed from a difference of nearby p' values), are reported and judged at
level 2. Amended in `docs/SYSTEM.md`'s REQ-N03 the same day.

**The elementary functions (Alex, 2026-11-25, after prompt 94).** The turbulence model and the wall
functions are the first modules whose elementwise blocks call a logarithm or a power: the reference's
`np.log` and its cubes `x**3` on arrays, and `c_mu**0.25`, `k**1.5` and `x**2` on Python's floats. The
core calls the C library's `log` and `pow`, behind two functions of the module `elementary` in a source
file of their own, so that the compiler does not replace a power of a known exponent by the products it
expands one to. NumPy calls the C library for both too, except on a processor with AVX-512, where it
forms `np.log` and the cube with loops of its own (an assembly routine of Intel's SVML for the cube) that
differ from the C library's by one unit in the last place on some values
(`docs/reports/phase6_turbulence.md`, T6). The core's bit-for-bit target for these blocks is the Python
reference at the x86-64-v3 level the core builds for (`-march=x86-64-v3`, CLAUDE.md): NumPy with its
AVX-512 loops off (`NPY_DISABLE_CPU_FEATURES=X86_V4`), where NumPy calls the C library too. The parity
tests of those blocks ask for that level (the fixture `libm_numpy`; CI's core job sets the variable;
elsewhere they skip, or fail under `CFD_CORE_REQUIRED=1`). With the loops on, the reference's own results
depend on the processor (the report's F2: a coupled solve's eps in the wall cells and, under RNG, its R
carry NumPy's rounding); those differences are measured and reported, and judged at level 2, and a test
of level 1's bound of 1e-12 runs in every environment. Amended in `docs/SYSTEM.md`'s contract row the
same day.

**ADR-016's "exactly".** ADR-016 asks the port to reproduce the implicit stop exactly. At level 1
it does: given the reference's inputs, the copied order gives the same leftover and the same
sweep, bit for bit. In a whole run the stop's inputs carry the upstream blocks' rounding, so the
stop can still land one sweep apart; level 2 admits that (section H, every stop within one) and
no more. ADR-016's Phase 6 consequence is annotated to say so.

## H. The end-to-end criterion

**What the probe found** (`docs/reports/phase6_design.md`, section 2; P1 to P8). On the dust
release, the door leak and the filter breach on 80x30 and the dust release and the breach on
160x60, each of seven legitimate changes (the two tolerances scaled by 1%, the inflow by
1 + 1e-15, the leftover summed in row-major order, and, added by this pass, each flow solve
stopped one outer iteration later) moved no decision: no arrival time of the 11,126 the
references reach left its step, no clear time its frame, no searched layout its cells, the
layouts' order did not change, and every budget stayed inside REQ-T05 by a factor of 89.8 or
more (the 160x60 dust release's leftover, 1.114e-6 of its supply, against 1e-4; P3, P3b, P4, P5, P6). A second run of the unchanged reference in another process was
bitwise, and the 80x30 references reproduce prompt 81's runs bitwise (P1, P1b). The fields
moved by two kinds of amount (P2, P8):

- *rounding propagated*: the inflow's 1e-15 and the pressure tolerance's changes, which can
  move a CG stop and on two runs moved none, left every field within about 1e-12 of its largest value;
- *a stop one iteration or sweep apart*: the diffusion tolerance moved Jacobi stops and the
  added variant the outer stop; the concentration moved by up to 2.7e-8 of its largest value
  and 5.8e-8 pointwise at the thresholds' decades, the flow fields by up to 7.8e-10.

A correct port does both: every reduction it forms rounds differently, and a stop whose test
sits within rounding of its threshold can end one iteration apart (ADR-013 C, ADR-016). The
second kind sets the band.

**The criterion proposed (REQ-N03 level 2).** A port's run of a benchmark scenario agrees with
the reference's when:

1. *every decision is equal*: each arrival time and each latency of a layout at the same step,
   each clear time at the same frame, the same searched cells under each rule and pool, the
   same order of the layouts, the same verdict of every class against REQ-T05. The one
   admissible exception is a decision whose deciding reading in the reference lies within the
   pointwise field limit below of its threshold at the deciding step, a crossing the band itself
   cannot settle; the probe met none, and a port result that claims one shows the reference's
   reading at that cell and step;
2. *every field is inside its limit*, each the largest the probe measured, times ten, rounded up
   to a decade: the flow fields (u, v, p, k, eps, nu_t) 1e-8 of each field's largest magnitude;
   the class fields 1e-6 of their largest, and 1e-6 pointwise where the reference reads at
   least a hundredth of the class's threshold; the sensor channels 1e-6 (from P2's 4.7e-8, as P8
   has no sensor column; review 85 S5); the accumulated leftover within 1e-8 of the supply of
   the reference's; the budget closing to 1e-12 of the supply, the reference's own check. The
   limits are read in three tiers (Alex, 2026-11-16):
   - *inside the measured spread* (P8's largest for that field, P2's for the sensor channels,
     and on 320x120 the spread step 6 measures): a pass;
   - *between the spread and the limit*: a pass only when the stop counts explain it, that is
     when the run's differing stops (item 3) are of the kind and number that moved the field
     that far in the probe, shown in the step's report; otherwise it is read as beyond the
     limit;
   - *beyond the limit*: a failure, read as "What a result outside the band means" below.
   The budget's closure is not tiered: it is the reference's own check, and it holds or fails;
3. *every stop is within one of the reference's*: the outer count of each flow state, and the
   CG and Jacobi counts are reported beside, not judged.

The factor of ten is a choice, not a measurement. Each variant changed one thing; a port
changes all its reductions at once, and the stops that sit within rounding of their thresholds
may flip together. The probe scaled the thresholds of two of the five stops by 1% (the pressure
CG's relative level and the transport's max-norm level; not the leftover's share,
`turbulence.tol` or the pressure floor) and moved the outer stop by one iteration. How many
stops each change flipped was not recorded, and on 80x30 the diffusion tolerance flipped none
(P1), so the class fields' limit rests on three 160x60 runs. If their 2.7e-8 is one flipped
sweep, ten covers about ten flips adding (review 85 S2); the middle tier asks the stop counts to
show that a result in it is of that kind. The flow fields' limit rests on the outer-stop
variant alone, added after the first queue's results: without it the same rule gives 1e-11
(review 85 S3), which a correct port's outer stop one iteration apart would exceed.
*Alternatives:* the limits as measured, with no factor, which a correct port could exceed by
adding two effects; a hundred, which would let a stop that differs by several iterations, a
defect in a stop's arithmetic, pass.

**On 320x120.** The probe ran 80x30 and 160x60 only (the prompt's grids). The band's flow
limit comes from the outer stop and its class limits from the Jacobi stops, both of which hold
on 320x120 too, but the product grid takes more steps. No 160x60 run had a second,
warm-started flow state, so the band holds no flow switch (review 85 S13). The end-to-end step
(section J, step 6) reruns the diffusion tolerance at 0.99 and the outer stop one later on the
320x120 dust release and door leak, the door leak for its two flow states (both converge on
320x120, `docs/reports/rerun79.md`), before it scores the core against the band there.

**What a result outside the band means.**

- *A decision differs and its reading is not marginal*: the port computes something the
  reference does not. The frames bracket the step where the fields first leave the band; the
  level 1 tests on that step's captured inputs find the block.
- *The decisions agree and a field is outside its limit*: either a defect that has not yet
  reached a decision, or more stops differing than the margin allows. The iteration counts tell
  which: counts within one of the reference's with fields outside the limit is a defect in the
  arithmetic; counts that differ by more than one at the same stop is a stop computed
  otherwise than section F states, a contract the port did not carry.
- *A budget verdict differs*: a defect, since the references sit 89.8 times or more inside
  REQ-T05 on every run.
- In none of these cases is the band widened to fit the port. If a port's change is shown to be
  legitimate and outside the band (a different, correct order of a stop's arithmetic, say), the
  change is made in the reference as a variant, the band remeasured with it, and the result
  goes to Alex.

**Single precision.** Decision 6 applies the same benchmark where single precision is used,
and Alex decided on 2026-11-16 that it is held to the same bar as double, the decisions and the
field limits with their tiers alike, to measure whether it can meet it. A single-precision
update rounds at about 6e-8, which is the size of the band's class-field limits before any
accumulation over 15,000 steps, so the limits may well exclude a single-precision stage. A
stage that does not meet the bar stays in double (decision 5: single precision only where a
measurement shows it pays), and its band reading is recorded beside its speed. A different bar
for single precision would be Alex's decision on those measurements, not a change made to fit.

## K. CLAUDE.md's compiled-code rules

Applied to CLAUDE.md with this record's acceptance (Alex, 2026-11-16). In "Project Structure", `csolver/` becomes
`core/` ("C++ core library, its tests and its binding; CMake"). "Language and Runtime":
"Performance-critical code: C++20 (the core library, `core/`), called through a nanobind
module; CUDA C++ at the Phase 6 CUDA step." "C Coding Standards" becomes "C++ Coding Standards":

- All compiled sources live in `core/`; one header per module in `core/include/cfdcore/`.
- Function and type names `snake_case` inside a namespace per module (`cfdcore::pressure`).
- No allocation inside a step: every array is allocated when a run or an interval is set up.
- Every public function documents its parameters, units and array shapes in a comment above it.
- Compiled with `-Wall -Wextra -Wpedantic -O2 -ffp-contract=off`; warnings fixed. (From
  2026-11-20 also `-march=x86-64-v3`, section A.)
- The core receives arrays and scalars; it has no knowledge of the configuration file, the
  boundary segments' names or types, file I/O, logging or the user. The boundary's per-face data
  are derived in Python and handed in; the core applies them inside the step, since the step is
  resident (ADR-017 decision 2).

The "What Gets Committed" list keeps `*.so` and build trees out. The Linux environment is outside
the checkout, so it needs no entry there.
